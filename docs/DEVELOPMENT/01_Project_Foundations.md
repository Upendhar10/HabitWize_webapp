# Project Foundations

This phase establishes the foundational structure of the project before implementing any project-specific functionality.

The goal is to set up the development environment, project workspaces, tooling, and core configurations required to build and maintain a modern full-stack application.

This phase includes:

- Setting up the frontend and backend workspaces.
- Configuring root-level workspace management.
- Establishing Git and development tooling.
- Setting up the initial frontend and backend foundations.

---

## 1. Frontend Project Foundations

### 1.1 `chore(frontend): initialize React app using Vite`

**What I did**

- Bootstrapped the React application using Vite.
- Chose TypeScript as the primary language for the frontend.
- Removed the default boilerplate code generated by Vite.

**Why**

- Chose Vite for its fast development server, modern build tooling, and streamlined React setup.
- Chose TypeScript to improve type safety, code maintainability, and developer experience as the application grows.

### 1.3 `chore(frontend): configure TypeScript settings`

**What I did**

- Enabled **`"strict": true`** to improve type safety and catch potential type-related issues earlier during development.

### 1.6 `chore(frontend): add environment variable validation`

**What I did**

- Created `.env` and `.env.sample` files to manage the environment variables required by the application.

- Added an environment variable validation function at `@/config/env.config.ts` to validate the variables loaded from the `.env` file before they are used by the application.

- Added checks to ensure required environment variables are present and have the expected types and values.

**Why**

- Environment variables are used to keep configuration and sensitive values such as API keys and database URLs outside the application source code, reducing the risk of accidentally exposing them in the codebase.

- The `.env.sample` file documents the environment variables required by the project without containing their actual sensitive values, making it easier for other developers to configure their local environments.

- Environment variables originate outside the application's type-safe code, so they should be validated before being consumed to prevent invalid or missing configuration from causing unexpected runtime issues.

- Strict validation provides early feedback by checking the presence, type, and validity of required environment variables during application initialization.

## 2. Backend Project Foundations

### 2.1 `chore(backend): initialize a node.js app using NPM`

**What I did**

- Initialized a Node.js project using `npm init`, which generates the `package.json` file.
- Installed the required dependencies using `npm install`, which generates the `package-lock.json file`.

**Why**

- `package.json` serves as the configuration and metadata file for the backend project. It defines project information, scripts, dependencies, and other npm configuration.
- `package-lock.json` locks the exact versions of the project's dependencies and their transitive dependencies, ensuring consistent installations across different environments.

---

### 2.2 `chore(backend): install and configure TypeScript`

**What I did**

- Installed `typescript`, `tsx`, and `@types/node` as development dependencies using `npm i -D typescript tsx @types/node`.

- Added the following scripts to `package.json`:

  ```json
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "build": "tsc",
    "start": "node dist/index.js"
  }
  ```

  - `dev`: Runs the application directly from TypeScript source files and automatically restarts when files change.
  - `build`: Compiles the TypeScript source code into JavaScript using the TypeScript compiler (`tsc`).
  - `start`: Runs the compiled JavaScript application from the `dist` directory.

- Created a `tsconfig.json` file and configured the TypeScript compiler according to the project's requirements.

**Why**

- Installed TypeScript as a development dependency because TypeScript is primarily needed during development and the build process; the production application runs the generated JavaScript.
- Installed `tsx` to execute TypeScript files during development without requiring a separate compilation step and to provide watch mode for automatic restarts.
- Installed `@types/node` to provide TypeScript type definitions for Node.js built-in APIs and globals.
- Used `tsc` for the production build because it is the TypeScript compiler responsible for type-checking and transpiling TypeScript into JavaScript.

---

### 2.3 `chore(backend): configure ESLint and Prettier`

**What I did**

- Installed `eslint` and `prettier` as development dependencies using `npm i -D eslint prettier`.
- Installed ESLint's JavaScript configuration package and Prettier compatibility configuration using `npm i -D @eslint/js eslint-config-prettier`.
- Installed `typescript-eslint` to enable ESLint support for TypeScript code.
- Encountered an upstream dependency compatibility issue between the current TypeScript version (`^7.0.2`) and the installed `typescript-eslint` version.
- Downgraded TypeScript to `^5.9.2` to maintain compatibility with the selected ESLint and TypeScript tooling.
- Created a `.prettierrc` file to configure formatting rules and a `.prettierignore` file to exclude specific files and directories from formatting.
- Created an `eslint.config.mjs` file to configure ESLint rules and integrate `typescript-eslint` with the project.
- Added the following scripts to `package.json`:
  ```
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "format": "prettier . --write",
    "format:check": "prettier . --check"
  ```
  - `lint` — Runs ESLint on the entire project `(.)` to identify code-quality and potential coding issues.
  - `lint:fix` — Runs ESLint and automatically fixes issues that ESLint can safely fix.
  - `format` — Runs Prettier on the entire project and automatically formats the files according to the configured rules.
  - `format:check` — Checks whether files are correctly formatted without modifying them. Useful for CI/CD pipelines.

**Why**

- **ESLint** is used to statically analyze the codebase, identify potential issues, and enforce consistent coding practices.
- **Prettier** is used to automatically format the codebase and maintain a consistent coding style.
- **`eslint-config-prettier`** disables ESLint rules that may conflict with Prettier, allowing both tools to work together without conflicting formatting rules.
- **`@eslint/js`** provides ESLint's recommended JavaScript configuration, establishing a sensible baseline for linting.
- **`typescript-eslint`** enables ESLint to understand and lint TypeScript-specific syntax and provides TypeScript-aware linting rules.
- **Downgrading TypeScript** was necessary to resolve the dependency compatibility issue and ensure that the ESLint and TypeScript tooling works reliably together.
