# Project Foundations

This phase establishes the foundational structure of the project before implementing any project-specific functionality.

The goal is to set up the development environment, project workspaces, tooling, and core configurations required to build and maintain a modern full-stack application.

This phase includes:

- Setting up the frontend and backend workspaces.
- Configuring root-level workspace management.
- Establishing Git and development tooling.
- Setting up the initial frontend and backend foundations.

## 2. Backend Project Foundations

### 2.1 `chore(backend): initialize a node.js app using NPM`

**What I did**

- Initialized a Node.js project using `npm init`, which generates the `package.json` file.
- Installed the required dependencies using `npm install`, which generates the `package-lock.json file`.

**Why**

- `package.json` serves as the configuration and metadata file for the backend project. It defines project information, scripts, dependencies, and other npm configuration.
- `package-lock.json` locks the exact versions of the project's dependencies and their transitive dependencies, ensuring consistent installations across different environments.

---

### 2.2 `chore(backend): install and configure TypeScript`

**What I did**

- Installed `typescript`, `tsx`, and `@types/node` as development dependencies using `npm i -D typescript tsx @types/node`.

- Added the following scripts to `package.json`:

  ```json
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "build": "tsc",
    "start": "node dist/index.js"
  }
  ```

  - `dev`: Runs the application directly from TypeScript source files and automatically restarts when files change.
  - `build`: Compiles the TypeScript source code into JavaScript using the TypeScript compiler (`tsc`).
  - `start`: Runs the compiled JavaScript application from the `dist` directory.

- Created a `tsconfig.json` file and configured the TypeScript compiler according to the project's requirements.

**Why**

- Installed TypeScript as a development dependency because TypeScript is primarily needed during development and the build process; the production application runs the generated JavaScript.
- Installed `tsx` to execute TypeScript files during development without requiring a separate compilation step and to provide watch mode for automatic restarts.
- Installed `@types/node` to provide TypeScript type definitions for Node.js built-in APIs and globals.
- Used `tsc` for the production build because it is the TypeScript compiler responsible for type-checking and transpiling TypeScript into JavaScript.

---

### 2.3 `chore(backend): configure ESLint and Prettier`

**What I did**

- Installed `eslint` and `prettier` as development dependencies using `npm i -D eslint prettier`.
- Installed ESLint's JavaScript configuration package and Prettier compatibility configuration using `npm i -D @eslint/js eslint-config-prettier`.
- Installed `typescript-eslint` to enable ESLint support for TypeScript code.
- Encountered an upstream dependency compatibility issue between the current TypeScript version (`^7.0.2`) and the installed `typescript-eslint` version.
- Downgraded TypeScript to `^5.9.2` to maintain compatibility with the selected ESLint and TypeScript tooling.
- Created a `.prettierrc` file to configure formatting rules and a `.prettierignore` file to exclude specific files and directories from formatting.
- Created an `eslint.config.mjs` file to configure ESLint rules and integrate `typescript-eslint` with the project.
- Added the following scripts to `package.json`:
  ```
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "format": "prettier . --write",
    "format:check": "prettier . --check"
  ```
  - `lint` — Runs ESLint on the entire project `(.)` to identify code-quality and potential coding issues.
  - `lint:fix` — Runs ESLint and automatically fixes issues that ESLint can safely fix.
  - `format` — Runs Prettier on the entire project and automatically formats the files according to the configured rules.
  - `format:check` — Checks whether files are correctly formatted without modifying them. Useful for CI/CD pipelines.

**Why**

- **ESLint** is used to statically analyze the codebase, identify potential issues, and enforce consistent coding practices.
- **Prettier** is used to automatically format the codebase and maintain a consistent coding style.
- **`eslint-config-prettier`** disables ESLint rules that may conflict with Prettier, allowing both tools to work together without conflicting formatting rules.
- **`@eslint/js`** provides ESLint's recommended JavaScript configuration, establishing a sensible baseline for linting.
- **`typescript-eslint`** enables ESLint to understand and lint TypeScript-specific syntax and provides TypeScript-aware linting rules.
- **Downgrading TypeScript** was necessary to resolve the dependency compatibility issue and ensure that the ESLint and TypeScript tooling works reliably together.

---

### 2.4 `chore(backend): configure path aliases with tsc-alias`

**What I did**

- Installed `tsc-alias` as a development dependency using `npm i -D tsc-alias`.
- Configured the `@/*` path alias in `tsconfig.json` to map to `./src/*`.
- Removed the deprecated/unnecessary `baseUrl` configuration.
- Updated the backend build command to run: `tsc && tsc-alias`

**Why**

- The backend already uses the `@/` alias to reference modules from the `src/` directory.
- TypeScript `paths` allows the compiler to understand these aliases during development and compilation.
- However, TypeScript does not rewrite those aliases in the emitted JavaScript.
- `tsc-alias` rewrites the compiled imports so Node.js can resolve them correctly at runtime.
- Running `tsc` followed by `tsc-alias` ensures the generated JavaScript contains runtime-resolvable import paths.

---

### 2.5 `chore(backend): add environment variables validation`

**What I did**

- Installed `dotenv` as a dependency using `npm i dotenv`.
- Created a `.env` file to store environment-specific configuration and sensitive values.
- Created a `.env.sample` file containing the required environment variable names without exposing actual values.
- Created `@/config/env.config.ts` to load and validate environment variables before they are used by the application.

**Why**

- `dotenv` allows the application to load environment variables from the `.env` file.
- Sensitive information such as credentials, database URLs, and client URLs should not be hardcoded in the source code or committed to the repository.
- Environment variables come from outside the application, so they should be **validated at startup** to ensure required values exist and have the expected format.
- `.env.sample` documents the environment variables required to run the backend while keeping their actual values private.
- Centralizing validation in `env.config.ts` prevents invalid configuration from reaching the rest of the application.

**What I did**

- Initialized a Node.js project at the repository root using `npm init -y`.
- Updated the generated `package.json` to serve as the **repository workspace** rather than as a standalone Node.js application.
- Configured the root workspace with the following:

- Provide a centralized location for installing and managing **Git-related development tools**.
- Keep Git tooling and configuration consistent across the entire repository.
- Standardize the project's Git history and commit conventions without coupling the root workspace to either application.

---

### 3.2 `chore(project): configure git hooks with husky and lint-staged`

**What I did**

- Initialized **Husky** at the repository root using `npx husky init`.
- This setup:
  - Installs `husky` as a development dependency.
  - Creates the root-level `.husky/` directory.
  - Creates the `.husky/pre-commit` hook.
  - Adds or updates the `"prepare": "husky"` script in the root `package.json` to ensure Husky is initialized when dependencies are installed.
- Installed **`lint-staged`** as a development dependency using: `npm install -D lint-staged`
- Configured the root-level `.husky/pre-commit` hook to execute: `npx lint-staged`
  - This ensures that linting and formatting checks are executed on staged files before a commit is created.
- Since the `frontend` and `backend` workspaces have **separate ESLint and Prettier configurations**, configured `lint-staged` to run the appropriate workspace-specific tooling for each staged file.
- Added a custom workspace command runner at: `/scripts/run-workspace-command.mjs`
  - This script determines the appropriate workspace for a staged file and executes the required command using that workspace's ESLint and Prettier configuration.
- Added the corresponding `lint-staged` configuration at: `/lint-staged.mjs`
  - This configuration delegates staged-file processing to the custom workspace command runner.
  - As a result, the pre-commit workflow is now:
    ```text
    git commit
        ↓
    Husky
        ↓
    .husky/pre-commit
        ↓
    lint-staged
        ↓
    Workspace-specific ESLint / Prettier
        ↓
    Commit proceeds only if the checks succeed
    ```

- Tested the `lint-staged` workflow with different file naming patterns, including: `git test.ts` and `git-test.ts`and verified that the staged files were correctly detected and processed as expected.

**Why**

- This setup establishes an automated **pre-commit quality gate** for the repository using **Husky** and **lint-staged**.

  - **Husky** is used to manage and execute **Git hooks**. In this setup, Husky triggers the `pre-commit` hook whenever a commit is attempted, allowing us to run validation before the commit is created.

  - **lint-staged** is used to run configured **linting and formatting commands only against files that are staged for commit**. This avoids unnecessarily processing the entire codebase and makes the pre-commit workflow faster and more focused.

- Because the `frontend` and `backend` workspaces have their own **ESLint and Prettier configurations**, the custom workspace command runner ensures that each staged file is validated using the appropriate workspace-specific configuration.

- Together, **Husky + lint-staged** provide an automated workflow that helps prevent code that violates the project's linting or formatting rules from entering the Git history.
